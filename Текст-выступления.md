# 🎤 Текст выступления — NewsAggregator
> Продолжительность ≈ 5–7 минут. Речевые вставки для ведущего — в квадратных скобках. Подсказки, что показывать — в скобках (слайд).

---

## 1. ВСТУПЛЕНИЕ (≈ 30 сек)

> (Слайд 1: название проекта, ФИО, группа)

Добрый день! Представляю вашему вниманию курсовой проект **NewsAggregator** — веб-приложение для автоматического сбора и классификации новостей из российских средств массовой информации.

Сегодня для получения новостей нужно ходить по нескольким сайтам, следить за каждым в отдельности. Мой проект решает эту задачу: система сама собирает новости из пяти источников, автоматически раскладывает их по рубрикам и показывает в удобном интерфейсе.

---

## 2. ЦЕЛИ И ЗАДАЧИ (≈ 30 сек)

> (Слайд 2: цель, задачи)

**Цель** — разработать веб-приложение, которое автоматически агрегирует новости и предоставляет персонализированную ленту.

**Задачи:**
1. Разработать модуль автоматического парсинга новостей из RSS-лент и HTML-страниц.
2. Реализовать автоматическую классификацию новостей по рубрикам.
3. Организовать хранение данных.
4. Разработать REST API и клиентское веб-приложение.
5. Реализовать систему аккаунтов с JWT-авторизацией.
6. Реализовать персональные рекомендации по интересам пользователя.

---

## 3. АРХИТЕКТУРА И СТЕК (≈ 60 сек)

> (Слайд 3: схема архитектуры, стек)

Система построена по **трёхслойной архитектуре**:

- **Доменный слой** — `NewsAggregator.Core`: сущности и интерфейсы, без зависимостей.
- **Слой данных и бизнес-логики** — `NewsAggregator.Infrastructure`: работа с базой, парсер, классификатор.
- **Презентационный слой** — `NewsAggregator.WebAPI`: REST-контроллеры, авторизация, Swagger.

Главное архитектурное решение: **зависимости направлены только внутрь**, каждый слой «не знает» о слоях выше.

**Технологии:** бэкенд — C# и ASP.NET Core на платформе .NET 10; база данных — SQLite с EF Core; авторизация — JWT-токены; пароли хэшируются алгоритмом BCrypt; логирование — Serilog. Фронтенд — React 19 с TypeScript и сборкой на Vite; общение клиента с сервером — через axios.

Можно отдельно отметить: пароль никогда не хранится в открытом виде, а база данных сама создаётся и обновляется миграциями при запуске.

---

## 4. БАЗА ДАННЫХ (≈30 сек)

> (Слайд 4)

Хранение реализовано через **EF Core** на SQLite — один файл `newsaggregator.db`, что упрощает установку и тестирование.

Основные сущности: **новости**, **категории (13 рубрик)**, **пользователи**, **история чтения**, **предпочтения** и **токены сброса пароля**.

Для защиты от дублей на поле URL новости установлен **уникальный индекс**, а на email и логин пользователя — тоже уникальные индексы.

---

## 5. ПАРСИНГ — САМЫЙ ВАЖНЫЙ МОДУЛЬ (≈40 сек из слайдов)

> (Слайд 5: источники, RSS и HTML)

Сбор новостей — ключевая часть проекта. Поддерживаются два типа источников.

**RSS-ленты** — это структурированный XML, который отдают Lenta.ru, ТАСС и RT. Парсер извлекает заголовок, ссылку, дату и картинку. Берутся последние 30 статей с каждого источника.

**HTML-страницы** — для РБК и «Известий», они не отдают RSS. Здесь заголовки извлекаются по HTML-построениям: например, у РБК это атрибут `data-role="title-link"`, а у Известий — CSS-класс карточки.

**Параллельность и картинки.** Если в статье нет превью, отдельный процесс делает запрос к странице и вытаскивает мета-тег `og:image`. Это выполняется с ограничением в 8 параллельных запросов.

Отдельно отмечу: вся работа идёт **в фоне**. Специальная фоновая служба запускается через минуту после старта приложения и парсит новости **каждые 30 минут**.

## 6. КЛАССИФИКАЦИЯ (≈40 сек)

> (Слайд 6)

После сбора каждая новость автоматически относится к рубрике. Используется **словарный классификатор**: в системе хранится расширенный словарь ключевых слов по каждой из 13 категорий — от политики и экономики до спорта и путешествий.

Классификатор считает совпадения слов заголовка со словарём каждой категории; побеждает рубрика с наибольшим количеством совпадений. Если совпадений нет — новость попадает в рубрику «Другое».

Такой подход быстрый и не требует обучения моделей.

## 7. АВТОРИЗАЦИЯ (≈40 сек)

> (Слайд 7: JWT схема)

Система аккаунтов построена на **JWT-токенах** — это компактный json-токен с подписью, который не хранит состояние на сервере.

При входе пользователь получает пару токенов: **короткий access-токен на 15 минут** и **долгий refresh-токен на 7 дней**, который хранится в базе.

Роли: первый зарегистрированный пользователь автоматически становится **администратором** и получает право запускать ручной парсинг кнопкой на странице. Остальные — обычные пользователи.

Пароли надёжно защищены: хэшируются алгоритмом **BCrypt** и не восстановимы обратно.

## 8. РЕКОМЕНДАЦИИ (≈30 сек)

> (Слайд: рекомендации)

Пользовательская лента включает персональные рекомендации **«Рекомендовано для вас»**.

Логика простая: система считает, какие 3 категории пользователь читает чаще всего, и предлагает новые свежие статьи именно этих категорий, исключая уже прочитанные. Если история чтения пуста — показаны случайные новые материалы.

Рекомендации обновляются автоматически, когда пользователь открывает статью.

## 9. ДОПОЛНИТЕЛЬНЫЕ ВОЗМОЖНОСТИ (≈30 сек)

> (Слайд: виджеты)

В интерфейсе есть дополнительные виджеты:
- **Курсы валют** — восемь основных валют по отношению к рублю, обновляются каждый час через бесплатное API;
- **Фильтры и поиск** — фильтрация по категории, дате популярности, поиск по тексту;
- **Счётчик просмотров** и ссылка на оригинал статьи;
- **Тёмная/светлая тема** — настраивается по желанию пользователя.

## 10. ЗАЩИТА КАРТИНОК И ИДЕАЛЬНЫЙ СЛУЧАЙ (≈30 сек)

> (Слайд: ImageProxy)

Так как новости приходят с разных ресурсов, я реализовал **собственный прокси-сервер изображений**: браузер не обращается к внешним сайтам напрямую — изображение сначала скачивается, кэшируется на диске на 7 дней и только потом отдаётся в интерфейс. Это защищает от блокировок «горячих ссылок» и ускоряет повторные загрузки.

Проверено в процессе работы: по итоговому итогу в базе находилось порядка **двухсот тридцати новостей**, картинками обеспечено около 80 процентов.

Итак, в рамках проекта реализовано:

## БЛИЦ-ОТВЕТЫ НА ЧАСТЫЕ ВОПРОСЫ

**Почему SQLite, а не PostgreSQL?**
Проект небольшой, нагрузки низкие. SQLite — это нулевая конфигурация: не нужен сервер, всё в одном переносимом файле. EF Core позволяет потом легко перейти на любую другую СУБД, поменяв драйвер и строку подключения.

**Как исключаются дубли новостей?**
Тройной контроль: уникальный индекс в БД на поле Url, уникализация в памяти во время парсинга и проверка существующей записи перед сохранением.

**Что если источник недоступен?**
Каждый источник обёрнут в защитный блок try/catch. Ошибка логируется, остальные источники парсится продолжают работать, сервис не падает.

**Зачем разделены access- и refresh-токены?**
Access живёт коротко (15 минут) — если он перехвачен, окно для злоумышленника минимально. Refresh хранится в базе, позволяет обновить пару и при каждом обновлении инвалидирует старый токен.

**Почему BCrypt для паролей?**
Это соль+хэш с регулируемой «дороговизной» вычисления — подбор перебором крайне трудоёмкий.

**Как строятся рекомендации?**
Топ-3 любимых категорий по истории чтения → свежие статьи этих категорий, ещё не прочитанных. Без истории — случайные материалы для знакомства.

**Что с неработающими картинками?**
Возможна сетьпроговая блокировка отдельных CDN (например, РБК недоступен по TLS) — это вне контроля кода. Проки удаляет остальные источники; карточка без картинки просто отображается без рамки.
